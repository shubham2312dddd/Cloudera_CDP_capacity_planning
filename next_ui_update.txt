Cloudera Infrastructure Sizing Studio
UI Updates — Simple Change List
Updated: 26 October 2026

This file explains the updates in simple words. Each item says what changed,
why it changed, what could happen without it, and what happens now.

1. Step-by-step screens and navigation
- Update: Added six steps, with Back, Next, and sidebar navigation.
- Why: Users can enter information in a clear order and go back to correct it.
- If not updated: Users may find the process confusing or have trouble fixing
  earlier answers.
- After update: Users can move through the steps and review their entries.

2. Separate environment profiles
- Update: Users can select Production, UAT, Development, and PoC together.
  Each environment keeps its own inputs and results.
- Why: Different environments can need different sizes.
- If not updated: Users may need separate sessions or mix different
  environments' numbers.
- After update: Each environment has its own cluster estimate. Their node
  counts are not added together.

3. Data unit choices
- Update: Initial data can be entered in TB or GB. Daily ingest can be entered
  in GB/day or TB/day.
- Why: Users should not have to convert these values by hand.
- If not updated: A unit mistake could make the storage estimate much too
  large or too small.
- After update: The app converts the values for its calculations and shows the
  chosen units in the review and reports. It uses the workbook rule of 1024 GB
  per TB.

4. Workload inputs
- Update: Added inputs for peak workload vCores and RAM, as well as data
  growth, design years, cold data, and compression.
- Why: Storage alone does not show how much computing power a workload needs.
- If not updated: The estimate may not have enough information to size workers
  for CPU and memory needs.
- After update: The sizing calculation can compare storage, CPU, and memory
  needs.

5. Hardware and planning settings
- Update: Added editable worker hardware, storage protection, usage, minimum
  worker, and high-availability settings.
- Why: Hardware and planning choices affect the number of nodes needed.
- If not updated: The estimate may use assumptions that do not match the
  customer's plan.
- After update: Users can change these settings for each environment and see
  their effect on the estimate.

6. Base-only and Data Services choices
- Update: Added a platform choice for Base only or Base + Data Services.
- Why: Data Services should only be counted when it is part of the requested
  design.
- If not updated: Users could mistake an excluded Data Services estimate for
  zero or think it was included.
- After update: Base-only results say Data Services was not calculated.
  Data Services inputs are available when that scope is selected.

7. Data Services workload inputs
- Update: Added editable Data Services workload rows and worker settings.
- Why: Different services and workloads use different amounts of CPU, memory,
  block storage, and cache.
- If not updated: The Data Services estimate may not reflect the expected
  workloads.
- After update: The app uses the entered workloads and settings when it
  calculates Data Services capacity.

8. Review before calculating
- Update: Added a review step showing environment inputs, units, changed
  defaults, and validation messages.
- Why: Users should be able to check their entries before using the results.
- If not updated: A typing mistake or changed assumption could go unnoticed.
- After update: Users can correct entries before confirming. If inputs change
  later, the app asks for a new review before showing results or exports.

9. Results and calculation details
- Update: Added worker and master counts, sizing reasons, storage forecasts,
  calculation details, warnings, and architecture reminders.
- Why: Users need to understand where the estimate came from and what it
  includes.
- If not updated: Users may see a node count without understanding its limits
  or assumptions.
- After update: Users can inspect the estimate and see important items that
  still need an architecture review.

10. What-if scenarios
- Update: Added a tool to test larger data and workload needs against the
  confirmed estimate.
- Why: Users may want to see how growth could change the required capacity.
- If not updated: Users would have to change their main inputs to explore a
  possible future case.
- After update: Users can view separate data, compute, and combined scenarios
  without changing the confirmed inputs.

11. Downloads and reports
- Update: Added JSON, CSV, and printable HTML downloads for each environment.
- Why: Users need to share or keep the inputs and results.
- If not updated: Users may have to copy results by hand, which can cause
  mistakes.
- After update: Downloads include the environment, scope, inputs, results, and
  planning-rule details used for that estimate.

12. Optional AI helpers
- Update: Added optional AI tools to read customer notes and review
  architecture. The sizing calculations do not depend on these tools.
- Why: They can help organize requirements and identify questions to review.
- If not updated: Users would need to read and summarize customer notes
  entirely by hand.
- After update: Users can preview extracted values before applying them.
  AI review gives advice but does not change calculated node counts.

13. High/Medium priority planning features from the feature matrix
- Update: Added optional per-data-class forecasts with retention, audit/log
  growth, compression, cold-data protection, average-file-size object counts,
  and workload CPU/RAM factors. Added selectable Ozone EC schemes, environment
  capacity scaling, optional Kafka and Kudu estimates, manual dedicated
  service/GPU node inventories, connected-environment Control Plane overhead,
  year-by-year worker forecasts, a separate
  environment node roll-up, and an indicative Base CCU/data allowance
  comparison.
- Why: A single blended data volume and one total-node result can hide
  materially different data, workload, stream-processing, environment, and
  entitlement assumptions.
- After update: Class calculations and dedicated service estimates are
  visible in results and available in exports. Per-node Kafka capacities,
  workload factors, licensing allowances, and environment scales are editable
  assumptions and must be validated with the design team.

14. Save and reopen sizing projects
- Update: Added portable JSON project download and upload for client details
  and environment profiles.
- Why: Users need to continue a sizing project after closing the browser.
- After update: A reopened project returns to the first step and requires a
  fresh review and confirmation before results can be used.

Important note
These results are planning estimates, not a final hardware order. Check the
Cloudera version, workload, hardware, licensing, network, high availability,
and disaster recovery requirements with the appropriate experts before
procurement.

























===========================Suggestions================================================








Further improvements and implementation status
The list below distinguishes completed UI updates from remaining validation
work. It focuses on preventing mistakes and making estimates easier to trust.

1. Verify the formulas against the workbook
- Improvement: Compare the app's calculations with the matching workbook
  formulas and record the approved example inputs and outputs.
- Why it is worth doing: Correct node counts matter more than extra screen
  features.
- If skipped: A calculation difference could go unnoticed and lead to a
  misleading estimate.
- Priority: Highest. Do this before using estimates for customer decisions.

2. Add a test for the full results and downloads
- Improvement: Add automated checks that inputs, calculated counts, and
  downloaded reports all agree, including Base-only and Base + Data Services.
- Why it is worth doing: It helps catch accidental changes that break
  calculations or make reports disagree with the screen.
- If skipped: A future update could quietly change a result or produce an
  incorrect download.
- Priority: High. Basic calculation and unit tests already exist; extend
  those tests to cover the full user-facing result and export flow.

3. Correct the compression field label
- Improvement: Change “Expected compression ratio (%)” to a clear label such
  as “Expected compression ratio (x)” and explain that it is a multiplier.
- Why it is worth doing: The app calculates this as a ratio, for example 3x,
  not as a percentage.
- If skipped: Users may enter or read the value as a percent and get the
  wrong idea about the storage estimate.
- Status: Implemented. The current field is labeled “Expected compression
  ratio (x)” and help text explains that it is a multiplier.

4. Make AI apply targets clear
- Improvement: Let users choose which environment receives extracted AI
  values.
- Why it is worth doing: Different environments often have different
  workloads and sizes.
- Status: Implemented. AI values are applied only to the environment chosen
  in the target selector.

5. Add save and reopen for sizing projects
- Improvement: Let users save a project and later reopen its customer details,
  environment inputs, and results.
- Why it is worth doing: It supports ongoing planning and makes it easier to
  continue work after closing the app.
- If skipped: Users may have to re-enter information or rely on downloaded
  files to restore a project.
- Status: Implemented as portable JSON download/upload. Files are local and
  must be protected under the organization's customer-data handling rules.

Suggested order
Next, verify formulas against the source workbook and add automated checks
that compare screen results with JSON, CSV, and printable report exports.
Validate customer-supplied workload factors, Kafka capacities, and licensing
assumptions against the exact Cloudera version and target hardware.
