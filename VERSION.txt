Release notes — First semantic version and documentation update

1. Version identifier
- Issue: The previous identifier (2026.10.17.3) used a date-based format and did not clearly communicate a conventional release sequence.
- Why changed: Adopted 1.0.0 as the first semantic version for the current application and retained the prior identifier below as historical context.
- If not changed: Team members could have difficulty identifying the current release and relating changes to one another.
- Status: Documentation/version label only; no application behavior changed in this release.

2. Change rationale
- Issue: The existing change list described features but did not consistently explain the user-facing issue, reason for the change, or impact if the issue remained.
- Why changed: Updated next_ui_update.txt with a control-by-control issue / why changed / if not changed / status record.
- If not changed: Reviewers could see what was implemented but not why it mattered or what risk it addressed.
- Status: Documentation updated. Existing implementation and test results are carried forward from 2026.10.17.3.

3. Historical runtime incident
- Issue: The previous release's browser showed an ImportError because a running Streamlit process retained a stale engine module.
- Why changed: Recorded the actual recovery (restart the process to load the already-updated engine) for traceability.
- If not changed: Future maintainers might look for an unnecessary source-code workaround or repeat the troubleshooting.
- Status: Resolved in the previous release; the app and health endpoint were verified after restart.

Feature context carried forward:
- The what-if scenarios and their documentation were implemented in version 2026.10.17.3. This documentation release does not claim to introduce that feature again.

Prior implementation history (carried forward from version 2026.10.17.3):

Changes in the earlier cumulative implementation:
- Added non-destructive what-if sensitivity scenarios for Base data volume, peak CPU/RAM demand, and combined changes; included results in the UI, JSON, and printable HTML report.
- Documented field units, scenario assumptions, and the distinction between raw disk capacity and usable storage.
- Kept full precision in sizing calculations; round only the displayed forecast values.
- Added numeric validation for invalid and overflowing Base and Data Services inputs.
- Added the workbook rules version and source to the UI and exports.
- Improved metric-card contrast for light and dark themes.
- Clarified Base-only Data Services behavior and added a link to change scope.
- Added a review and confirmation step before final results.
- Require review confirmation for the exact current inputs before results/exports; changed inputs invalidate the confirmation.
- Clarified percentage labels, displayed capacity figures, sizing drivers, and remaining raw capacity.
- Expanded HTML, JSON, and CSV reports with current scope, inputs, rules, warnings, and sizing details.
- Added regression checks for workbook example values, every Base sizing driver, invalid values, and calculation precision.
- Added separate environment profiles and results; counts are not combined across environments.
- Added TB/GB and GB/day/TB/day input selectors, normalized to canonical units with the approved 1024 conversion.
- Added engine-level per-environment calculation and tested separate Base-only versus Base + Data Services totals.
- Keep saved environment profiles when selections change; prevent continuing with no selected environment.
- Include Data Services input units in the per-environment exports.
- Documented that workbook sample defaults are 3x compression and 40% cold data.
- Renamed the initial data input to “Initial raw data volume,” removing “day-1” wording.
- Clarified peak concurrent CPU demand as total vCores at peak concurrency and peak memory demand as total GB RAM at peak concurrency, including their use in CPU/memory worker sizing.
- Fixed report/export unit-map indentation so the Streamlit app compiles and runs.
